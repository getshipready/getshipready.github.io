@supabase/server adapters are removed on December 1: migrate without making your endpoints public

If your API uses withSupabase from @supabase/server/adapters/hono (or /h3, /elysia, /nestjs), you have until December 1, 2026. Supabase's changelog: "They will be removed from the package on December 1, 2026."

The migration is small. The risk is one step that looks right, compiles, and quietly makes a signed-in-only endpoint public. Supabase's frameworks guide says it plainly: "One step in that migration can open an endpoint up without an error."

Are you affected?

Search your code for @supabase/server/adapters. Every hit is a route group to move. Note the auth value on each withSupabase(...) call. Supabase: "A bare withSupabase() counts as auth: 'user'."

Not affected: withSupabase(config, handler) imported from @supabase/server itself, the pattern Supabase recommends for Edge Functions. The changelog: "withSupabase(config, handler) is not deprecated."

The trap: withClaims is not a login check

The replacement uses middleware "entries". Two of them look interchangeable and are not:

  • withRequiredClaims() rejects a request with no valid user token before your handler runs (401 MISSING_CREDENTIALS).
  • withClaims() adds the caller's claims if a token is there. Supabase's reference: "withClaims is not an auth gate. It never rejects a request that has no token."

The changelog: "Do not use withClaims() in place of auth: 'user'. The adapter rejected anonymous requests. withClaims() lets them through with jwtClaims: null, which turns a 401 into a 200 with no error."

Nothing breaks in testing (you're signed in), the typecheck passes, and the route now answers anyone. If the handler uses an admin client or reads by an id from the URL, that is a data leak.

The safe swap

Old adapter configUse instead
auth: 'user', or no configwithRequiredClaims()
auth: 'none'nothing (client entries only)
auth: 'publishable' or auth: 'secret'keep withSupabase; there is no bridge entry

Hono example from Supabase's frameworks guide. First copy their hono/supabase-middleware.ts bridge into your project; it needs @supabase/server 1.6.0+ and Node 22+, with @supabase/middleware as a direct dependency.

import { withRequiredClaims } from '@supabase/server/middleware/required-claims'
import { withSupabaseClient } from '@supabase/server/middleware/client'
import { toHono } from './lib/supabase-middleware.js'

const app = new Hono()
  .use('*', toHono([withRequiredClaims(), withSupabaseClient()]))

Then rename call sites. The adapter gave you c.var.supabaseContext; the entries give flat keys. supabaseContext.userClaims.id becomes c.var.jwtClaims.sub.

Check it in one minute

  1. After deploying, call every route that used to need a login, with no token:
    curl -i https://YOUR_API/todos
    Expect 401 with code MISSING_CREDENTIALS. A 200 means the route is open. Run this only against your own API.
  2. Grep for the trap:
    grep -rn "withClaims()" src/
    Every hit should be a route that is meant to be public, or a handler that checks jwtClaims is not null and returns 401 itself.
