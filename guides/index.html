Each guide covers one common Supabase or Stripe mistake in Lovable, Bolt and Cursor apps, with a check you can run yourself.

  • Clerk or a custom OIDC provider on Supabase: 3 RLS traps when your app trusts another issuer
    Supabase now lets you add any OIDC provider from the Dashboard. Three easy mistakes turn signed-in users into anon, push you towards using (true), or let users from one issuer match another's rows. Fixes and a 1-minute check.
  • @supabase/server adapters are removed on December 1: migrate without making your endpoints public
    The Hono, H3, Elysia and NestJS adapters go away on 1 Dec 2026. One migration step (withClaims instead of withRequiredClaims) turns a 401 into a 200. The safe swap and a 1-minute check.
  • Supabase edge function returns 401 "Invalid JWT" after switching to the new API keys: the safe fix
    Moved to sb_publishable / sb_secret keys and your edge functions now return 401 Invalid JWT? Here's the fix, and the step that keeps the function from going public.
  • Supabase is retiring the eyJ anon and service_role keys: the safe migration for Lovable and Bolt apps
    Supabase says the legacy anon and service_role keys go away by the end of 2026. How to tell if your Lovable, Bolt or Cursor app still uses them, the 10-minute swap, and the one mistake that puts your secret key in the public bundle.
  • Supabase 42501 "permission denied for table" after the Oct 30 change: the safe fix
    New tables return 42501 since the October 30, 2026 Data API change. The fix is a GRANT, but copying the hint's GRANT ... TO anon can open a table to everyone. The safe order for Lovable, Bolt and Cursor apps.
  • URL scan, two-account test or repo check: what each one can see

  • Login isn't access control: the second-account test for vibe-coded apps

    Lovable and Supabase show RLS as enabled, but a logged-in user can still read other people's rows. A 10-minute two-account test for every verb (select, insert, update, delete), plus the official pgTAP route.
