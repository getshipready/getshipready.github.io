URL scan, two-account test or repo check: what each one can see

There are now plenty of free pre-launch checks for vibe-coded apps. They aren't interchangeable. Each one looks from a different place, so each one misses something the others catch.

1. The outside-in URL scan

What it is: you paste your live URL and a tool reads what any visitor's browser receives: the HTML, the JavaScript bundles, response headers and the certificate. Most need no signup and finish in under a minute.

Good at: secret keys shipped in the frontend (Stripe secret keys, OpenAI keys, Supabase service_role), missing security headers, HTTPS problems, and spotting that your bundle contains Supabase or Firebase settings worth checking. Some tools go further and test table access once you prove you own the app.

Can't see: anything behind the login. A URL scan never acts as a signed-in user, so it can't tell whether user B can open user A's records. It also can't read code that isn't shipped to the browser: your database policies, edge functions, migrations and git history.

2. The signed-in two-account test

What it is: you (or someone you hire) create two ordinary accounts that aren't invited to each other's data, then try to read, edit and delete one account's records from the other. Steps are in Login isn't access control.

Good at: the most common serious bug in AI-built apps: policies that say "anyone signed in" instead of "the owner", auto-join on sign-in, UI-only hiding, and IDs in URLs that load for anyone. It tests the real deployed app, so it catches what actually happens, not what the code seems to say.

Can't see: paths you didn't think to try, tables your UI never touches, and leaked keys. It also takes 10 minutes per flow and has to be redone after each big AI edit. Paid human QA services run this test by hand for you if you'd rather not.

3. The repo check

What it is: a scan of your code and migrations (locally, or by a tool you give repo access).

Good at: tables created without row-level security, using (true) policies, policies with no with check, functions that bypass RLS, secrets committed to git history, and vulnerable dependencies, including tables no page links to yet.

Can't see: settings changed in a dashboard but not in code, and how the live app behaves. Code can look right and still be deployed differently.

Which to run before launch

Check              Sees                         Misses
URL scan           shipped keys, headers, TLS   anything behind login, DB rules
Two-account test   real cross-user access       untouched tables, keys, history
Repo check         every policy + git history   dashboard-only changes, live state

If you only have 30 minutes: run a free URL scan, run the two-account test on your main record type, and scan the repo for RLS-off tables and committed secrets. Each one covers a blind spot of the other two.
