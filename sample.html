  2. [CRITICAL] SEC-001 OpenAI/Anthropic API key committed in env file (Sentinel · Security) at .env:6
    • Why: Anyone with repo or bundle access can use this key: bills, data access, account takeover.
    • Fix: Move the value to your host's env settings (Vercel/Netlify/Supabase secrets), reference it only from server code, and ROTATE the key now.
  3. [CRITICAL] SEC-001 Supabase service_role key committed (Sentinel · Security) at .env:4
    • Why: The service_role key bypasses ALL Row Level Security. Whoever has it owns your database.
    • Fix: Rotate it in Supabase (Settings → API → JWT / API keys), keep it only in server-side env vars, never in the repo.
  4. [CRITICAL] SEC-002 .env file is not git-ignored (Sentinel · Security) at .env:1
    • Why: Your keys will be committed and pushed. Public repos are scraped for keys within minutes.
    • Fix: Add .env* and !.env.example to .gitignore, git rm --cached .env, then ROTATE every key that was ever committed (removing it from git history is not enough).
  5. [CRITICAL] SEC-003 Secret exposed to the browser via public env prefix: NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY (Sentinel · Security) at .env:4
    • Why: Variables prefixed NEXT_PUBLIC_/VITE_/EXPO_PUBLIC_ are inlined into the JavaScript bundle that every visitor downloads.
    • Fix: Rename without the public prefix, read it only in server code (API route, server action, edge function), rotate the key.
  6. [CRITICAL] RLS-001 Table payments has Row Level Security disabled (Warden · Supabase RLS & storage) at supabase/migrations/001_init.sql:26
    • Why: With RLS off, anyone holding your public anon key (it is in your frontend) can read, edit and delete every row via the REST API.
    • Fix: alter table public.payments enable row level security; then add explicit policies for each operation the app needs (see supabase-rls-patterns.md).
  7. [CRITICAL] RLS-002 profiles: policy "Profiles are viewable by everyone" lets anyone read every row (incl. email, is_pro, role) (Warden · Supabase RLS & storage) at supabase/migrations/001_init.sql:9
    • Why: using (true) on SELECT means public read for anon and authenticated users alike. Emails/roles become a scrapeable list.
    • Fix: Restrict to the owner: using (auth.uid() = id). If some fields must be public, expose them through a view or a separate public_profiles table with only safe columns.
  8. [CRITICAL] RLS-004 profiles: users can update their own privileged columns (is_pro, role) → self-promotion to admin/pro (Warden · Supabase RLS & storage) at supabase/migrations/001_init.sql:10
    • Why: The policy lets a user update ANY column of their own row, including role/plan flags. One API call from the browser console makes them admin or Pro for free.
    • Fix: Move privileged flags to a table users cannot write (e.g. entitlements, written only by the webhook with the service role), or revoke table-wide and re-grant safe columns only: revoke update on public.profiles from authenticated, anon; grant update (display_name, avatar_url) on public.profiles to authenticated; plus with check. (A column-level revoke alone does nothing while the table-level grant exists.)
  9. [CRITICAL] RLS-006 Supabase client built with the service_role key in a shared/client module (RLS bypassed app-wide) (Warden · Supabase RLS & storage) at src/lib/supabaseClient.ts:6
    • Why: Every file importing it (5 found: src/app/admin/page.tsx, src/app/api/notes/route.ts, src/app/api/stripe/webhook/route.ts, src/app/billing/success/page.tsx, src/components/NoteList.tsx) talks to the DB as superuser; in client components the key ships to the browser. Your RLS policies do nothing.
    • Fix: Use the anon key + user session in the browser (createBrowserClient), and a separate server-only admin client (import 'server-only') used solely in webhooks/cron.
  10. [CRITICAL] AUTH-002 API route changes data without checking who is calling (Keymaster · Auth) at src/app/api/notes/route.ts:9
    • Why: Anyone on the internet can call this endpoint directly (no UI needed) and modify or delete other users' data.
    • Fix: At the top of the handler: const { data: { user } } = await supabase.auth.getUser(); if (!user) return new Response('Unauthorized', { status: 401 }), then scope the query: .eq('user_id', user.id).
  11. [CRITICAL] PAY-001 Stripe webhook does not verify the signature (Tally · Payments) at src/app/api/stripe/webhook/route.ts:5
    • Why: Anyone can POST a fake checkout.session.completed to this URL and get Pro for free.
    • Fix: Read the raw body (await req.text()), then stripe.webhooks.constructEvent(body, req.headers.get('stripe-signature'), process.env.STRIPE_WEBHOOK_SECRET); return 400 on failure.
  12. [CRITICAL] PAY-002 Paid access granted from the browser / success page (Tally · Payments) at src/app/billing/success/page.tsx:9
    • Why: Visiting /billing/success (or running the same update from devtools) unlocks Pro without paying.
    • Fix: Grant entitlements ONLY in the verified webhook using a server-side client. The success page should just show 'processing' and poll your DB.
  13. [CRITICAL] PAY-003 Checkout price comes from the client request (Tally · Payments) at src/app/api/checkout/route.ts:11
    • Why: A user can edit the request and pay $0.50 for your $49 plan.
    • Fix: Use fixed Price IDs from your Stripe dashboard (line_items: [{ price: process.env.STRIPE_PRICE_PRO, quantity: 1 }]) and look up the plan server-side.
  14. [HIGH] SEC-004 Unsanitized HTML rendering (stored XSS risk) (Sentinel · Security) at src/components/NoteList.tsx:22
    • Why: If users can write the content, they can run JavaScript in other users' sessions and steal their tokens.
    • Fix: Render as text, or sanitize with DOMPurify (DOMPurify.sanitize(html)) / a markdown renderer that escapes HTML.
  15. [HIGH] RLS-003 notes: insert policy "Users insert notes" accepts any row (with check (true)) (Warden · Supabase RLS & storage) at supabase/migrations/001_init.sql:23
    • Why: Users can insert rows owned by someone else (spoofed user_id) or spam the table.
    • Fix: with check (auth.uid() = user_id) and set user_id default auth.uid().
  16. [HIGH] RLS-004 notes: update policy "Users update own notes" has no WITH CHECK (ownership can be reassigned) (Warden · Supabase RLS & storage) at supabase/migrations/001_init.sql:24
    • Why: Without WITH CHECK, a user can update their row and set user_id to someone else's id (or move data between tenants).
    • Fix: Add with check (auth.uid() = user_id) mirroring the USING clause.
  17. [HIGH] RLS-005 Storage bucket exports is public and its name suggests private files (Warden · Supabase RLS & storage) at supabase/migrations/001_init.sql:35
    • Why: Files in a public bucket are readable by anyone who has or guesses the URL; listing may also be possible via policies.
    • Fix: Make the bucket private and serve files with createSignedUrl(path, 60) after checking ownership; add storage.objects policies scoped to auth.uid().
  18. [HIGH] AUTH-001 Admin access enforced only in the browser (Keymaster · Auth) at src/app/admin/page.tsx:18
    • Why: Client-side checks hide the UI but not the data: the queries run anyway and anyone can call them from devtools.
    • Fix: Enforce on the server: RLS policy using an is_admin() security-definer function or a server route that verifies the role from the DB before querying. Protect /admin in middleware.
  19. [HIGH] PAY-004 No STRIPE_WEBHOOK_SECRET configured anywhere (Tally · Payments) at .env.example
    • Why: Signature verification is impossible without the endpoint secret.
    • Fix: Create the endpoint in Stripe → Developers → Webhooks, copy whsec_… into your host env as STRIPE_WEBHOOK_SECRET, and document it in .env.example.
  20. [HIGH] DEP-001 1 env var(s) used in code but missing from .env.example: NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY (Pilot · Deploy) at .env.example
    • Why: The #1 cause of 'works locally, broken on Vercel': the variable was never set in the host. Undocumented vars also block handover.
    • Fix: Add every var to .env.example (empty values) and set them in Vercel → Settings → Environment Variables for Production AND Preview.

Manual checks a static scan cannot do

  • [ ] Sentinel: Run npm audit --omit=dev (or pnpm audit) and fix critical/high advisories in production dependencies.
  • [ ] Sentinel: If any key was ever committed, rotate it even if the repo is private, and check provider logs for use.
  • [ ] Sentinel: Scan the deployed site with securityheaders.com and confirm headers are present in production, not just in config.
  • [ ] Warden: Run rls-live-check.sql in the Supabase SQL editor: migrations can differ from what is live (dashboard edits). Paste the output to Warden.
  • [ ] Warden: Test as an attacker: with only the anon key, curl "$SUPABASE_URL/rest/v1/<table>?select=*" -H "apikey: $ANON" for every table. Expect [] or 401 for private tables.
  • [ ] Keymaster: Confirm email confirmation is ON and the Site URL / Redirect URLs in Supabase Auth match your production domain (not localhost).
  • [ ] Keymaster: Try password reset and OAuth login on the production domain; check the redirect lands on HTTPS prod, not a preview URL.
  • [ ] Tally: In Stripe test mode, run stripe listen --forward-to localhost:3000/api/stripe/webhook and stripe trigger checkout.session.completed; confirm the user is upgraded once, and that a forged unsigned POST returns 400.
  • [ ] Tally: Handle customer.subscription.deleted and invoice.payment_failed so cancellations and failed renewals remove access.
  • [ ] Pilot: Run a production build locally (npm run build && npm start) before every deploy; fix all errors, don't ignore them.
  • [ ] Pilot: Set env vars separately for Production and Preview in Vercel; never point Preview at the production database with the service key.
  • [ ] Torque: Run Lighthouse (mobile) on the production URL; target LCP < 2.5 s, CLS < 0.1, INP < 200 ms.
  • [ ] Torque: In Supabase → Advisors, review Performance advisor warnings (unindexed foreign keys, RLS initplan).
  • [ ] Medic: Reproduce every reported bug with exact steps before fixing (don't fix what you can't reproduce). Use templates/bug-report.md.

Static heuristics, not a penetration test. A clean section means no known pattern matched, not that the area is safe. Review every fix before merging.
